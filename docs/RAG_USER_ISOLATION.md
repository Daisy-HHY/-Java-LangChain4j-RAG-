# RAG 用户隔离与历史数据迁移

## 访问规则

- 上传文档为私有资料，向量 metadata 必须包含 `knowledge_id`、`user_id`、`visibility=PRIVATE`。
- 普通问答和 SSE 问答均显式传递认证用户 ID，检索条件在向量库内、Top-K 之前执行：
  `(visibility = PRIVATE AND user_id = 当前用户) OR visibility = PUBLIC`。
- 降低相似度阈值不会取消用户过滤。没有用户 ID 时只能检索显式共享资料。
- 上传或私有向量写入缺少有效用户 ID 时拒绝操作，不自动发布为共享。
- `addSharedDocuments` 是显式发布共享资料的系统接口；开发环境 CSV/教材导入只允许管理员调用。
- 管理员身份取自当前数据库角色，不沿用已降权用户的旧令牌角色。
- 无完整访问元数据的旧向量默认不参与检索。

## 已有数据库迁移

代码不会自动清空向量表，未确认归属的历史资料也不会自动公开。

1. 暂停上传和问答写入，对数据库做完整备份；记录各知识库及切块数量。
2. 核对 `knowledge_base.user_id` 的真实归属。现有认证初始化器可能将历史空归属分配给默认管理员，应核实这是否符合实际所有权。
3. 有明确用户归属且有持久化切块的 READY 知识库，可执行一次启动重建：

   ```bash
   cd backend
   mvn spring-boot:run "-Dspring-boot.run.arguments=--kgqa.rag.reindex-on-startup=true"
   ```

   该命令行参数覆盖 YAML 中的固定 `false`；不要依赖未显式接入 YAML 的环境变量。
4. 重建先完成该知识库全部向量化，再删除同一 `knowledge_id` 的旧向量并写入新向量，保留用户归属。重复执行不会累积同一知识库的向量。
5. 用户归属为空或无效的知识库会跳过，不会仅凭空归属发布为 PUBLIC。确认是私有资料后修正所属用户再重建；确认可公开的系统资料应由管理员显式导入。现有共享向量在跳过重建时保持不变。
6. 没有 `knowledge_id` 的遗留向量不能安全关联来源。它们仍被访问过滤排除；审计后由管理员备份、清理或重新导入，不根据文本相同推断用户归属。
7. 查看重建日志并核对数量。重建异常会使启动失败；向量表替换并非原子事务，数据库写入故障时可能需要恢复备份或重试，因此应在维护窗口运行。
8. 恢复正常启动（去掉重建参数），再以两个不同用户检查普通问答和流式问答。已保存的历史聊天可能含修复前的回答，应另行审计，向量重建不会清除它们。

## 测试

```bash
cd backend
mvn clean test
```

自动化测试覆盖：私有/共享元数据、两种检索入口的过滤、相同向量下用户隔离、遗留元数据排除、删除、重复重建、模型失败保留旧索引、归属不明确跳过、上传用户传递、普通/流式问答及降阈值重试、共享导入授权、令牌角色降权。

这些测试使用模拟模型及内存向量库，不调用付费 AI API，也不等同于真实 PostgreSQL/pgvector 端到端测试。部署环境应另外验证数据库登录、vector 扩展、实际过滤和历史向量迁移。
