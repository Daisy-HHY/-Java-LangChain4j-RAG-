# KGQA RAG 系统优化计划

## 1. 目标

本计划用于指导当前医疗知识问答系统的后续优化。在开始实现前，先明确每个板块的优化方向、优先级、预期收益、风险和验收标准。

当前系统已经具备以下基础能力：

- Vue 3 前端聊天、知识库、历史会话页面
- Spring Boot 后端 API、认证、会话管理和知识库管理
- 基于 pgvector 的文档 RAG 检索
- 基于 Apache Jena TDB 的 kgdrug 知识图谱查询
- RAG 与知识图谱混合问答
- SSE 流式回答

后续优化的核心目标不是单纯增加功能，而是提升系统的安全性、回答质量、可解释性、可评估性和工程可维护性。

## 2. 总体路线

推荐采用“先打基础，再提升效果，最后产品化”的顺序推进。

| 阶段 | 重点 | 目标 |
|------|------|------|
| P0 | 安全隔离、评估、日志 | 先解决影响正确性和安全性的基础问题 |
| P1 | RAG 检索、文档分块、图谱结果结构化 | 明显提升回答质量和来源可解释性 |
| P2 | GraphRAG、医学安全护栏、性能和部署 | 提升项目展示价值和生产可用性 |

建议优先顺序：

1. 多用户向量隔离
2. RAG 评估集
3. 检索日志与调试信息
4. RAG 查询改写和重排
5. 文档分块和来源结构化
6. SPARQL 多列结果和图谱来源展示
7. GraphRAG 和医学安全护栏
8. 工程化部署和可观测性

## 3. P0 优化：必须优先完成

### 3.1 多用户向量检索隔离

#### 现状

系统已经有用户体系，`knowledge_base` 和 `chat_session` 都有 `user_id` 字段。知识库列表、删除、状态查询也按当前用户过滤。

但 RAG 向量检索目前没有接收当前用户 ID，也没有在向量检索时按用户过滤。向量 metadata 当前主要记录 `knowledge_id`，这会导致不同用户上传的文档在检索阶段可能互相召回。

#### 优化方案

- 向量入库时在 metadata 中写入 `user_id` 和 `knowledge_id`
- RAG 查询入口传入当前登录用户 ID
- `VectorStoreManager.searchWithScore` 增加用户过滤条件
- 删除向量时同时校验 `knowledge_id` 和 `user_id`
- 对历史数据提供一次性重建或补偿方案

#### 验收标准

- A 用户上传的文档，B 用户无法通过问答召回
- 删除文档时不会误删其他用户的向量
- 单用户场景下原有问答能力不退化

#### 风险

- 旧向量数据没有 `user_id` metadata，可能需要重建索引
- LangChain4j pgvector metadata filter 能力需要结合当前版本确认

### 3.2 RAG 评估集

#### 现状

项目已有一些手动测试工具类，但缺少稳定的自动化评估集。当前检索阈值、topK、prompt、分块策略的调整缺少量化依据。

#### 优化方案

建立一份小而稳定的医疗问答评估集，先覆盖 50 条左右样例：

- 知识图谱可回答的问题
- RAG 文档可回答的问题
- RAG 与 KG 都可能命中的问题
- 多轮追问问题
- 无资料问题
- 易幻觉问题
- 用药、治疗、病因、症状、并发症类问题

评估指标：

- recall@k：正确来源是否进入召回结果
- source hit rate：最终来源是否包含正确片段或图谱事实
- refusal accuracy：资料不足时是否拒答
- route accuracy：是否走了正确的 KG/RAG/混合链路
- groundedness：答案是否严格基于来源

#### 验收标准

- 可以通过命令一键运行评估
- 每次优化前后能对比指标变化
- 至少覆盖 KG、RAG、多轮、无资料四类场景

#### 风险

- 医疗问答标准答案需要人工整理
- 自动判断 groundedness 可能需要 LLM 评审或半自动人工复核

### 3.3 检索与路由日志

#### 现状

系统已有部分 debug 日志，但缺少完整的一次问答链路记录。出现回答错误时，不容易判断问题来自实体识别、SPARQL、向量检索、prompt 还是模型生成。

#### 优化方案

为每次问答记录结构化调试信息：

- requestId / sessionId / userId
- 原始问题和改写后问题
- 实体识别结果
- 意图识别结果
- 路由结果：KG、RAG、fallback
- SPARQL 语句和查询结果数量
- 向量召回 chunk、分数、knowledgeId、source title
- 最终模型调用耗时
- 是否触发无资料拒答

#### 验收标准

- 一次回答出错时，可以快速定位失败环节
- 评估脚本可以复用这些日志分析召回质量
- 日志不泄露敏感 token 和密码

## 4. P1 优化：核心效果提升

### 4.1 RAG 查询改写

#### 现状

多轮问答目前主要通过最近实体补全，例如“它怎么治”会尝试补成“某疾病的治疗方法”。这对简单追问有效，但对复杂上下文、多实体比较、指代消解不够稳定。

#### 优化方案

- 增加独立的 Query Rewrite 组件
- 输入最近 N 轮对话和当前问题
- 输出一个独立、明确、可检索的问题
- 对简单场景优先使用规则，复杂场景调用 LLM
- 保留原问题和改写问题，便于调试

#### 验收标准

- “它有什么症状”“这个病用什么药”等追问能稳定补全实体
- 多实体对话中不误用错误实体
- 查询改写失败时能回退到原始问题

### 4.2 混合检索与重排

#### 现状

RAG 当前是单路向量检索，固定 topK 和阈值。语义相似但关键词重要的医学问题可能召回不稳定。

#### 优化方案

- 第一阶段扩大向量召回数量，例如 topK 从 5 扩到 20
- 增加 rerank 阶段，从候选中选出最相关的 5-8 条
- 后续增加关键词检索或 PostgreSQL 全文检索，与向量检索融合
- 对药品名、疾病名、症状名这类实体词提高权重

#### 验收标准

- 评估集 source hit rate 提升
- 无关 chunk 进入最终 prompt 的比例下降
- 回答引用更集中、更准确

#### 风险

- rerank 会增加延迟和模型成本
- topK 扩大后如果没有重排，可能引入更多噪声

### 4.3 文档分块升级

#### 现状

当前分块策略是固定字符长度和固定 overlap。医学教材、说明书、PDF 表格和章节标题容易被切断，影响召回质量。

#### 优化方案

- 按标题、段落、列表、表格边界进行分块
- 保留文档标题、章节标题、页码、chunkIndex
- 对过长段落再做二级切分
- 对表格内容转换为可检索文本
- 分块参数配置化，方便不同类型文档调整

#### 验收标准

- 来源卡片能展示文档标题和片段位置
- 医学说明书、教材类文档的召回准确率提升
- chunk 内容不再频繁截断关键句

### 4.4 来源结构化

#### 现状

当前 `SourceItem` 主要包含内容和分数，图谱来源也被转换为普通字符串。用户无法清楚区分答案来自文档还是图谱。

#### 优化方案

扩展来源结构：

- sourceType：`DOCUMENT` 或 `GRAPH`
- content：来源内容
- score：召回分数
- knowledgeId：文档 ID
- documentTitle：文档标题
- chunkIndex：分块序号
- pageNumber：页码，可选
- graphSubject：图谱主语
- graphPredicate：图谱关系
- graphObject：图谱宾语

#### 验收标准

- 前端能区分文档来源和图谱来源
- 图谱问答能展示实体、关系和值
- 文档问答能展示标题、片段、分数

### 4.5 SPARQL 结果结构化

#### 现状

SPARQL 执行器当前主要取查询结果里的第一个绑定值，丢失多列结构和变量含义。对于复杂查询、比较查询、路径查询不够友好。

#### 优化方案

- 让 KG 查询返回结构化结果，而不是 `List<String>`
- 保留变量名、实体 URI、label、predicate
- 模板查询直接生成可解释的 graph source
- LLM 生成 SPARQL 后进行更严格校验
- 对查询结果为空、超时、语法错误分别处理

#### 验收标准

- 图谱回答能显示事实三元组或多列结果
- 比较类、统计类问题有扩展空间
- SPARQL 错误不会直接影响 RAG fallback

## 5. P2 优化：高级能力与产品化

### 5.1 GraphRAG

#### 目标

把当前“KG 优先，失败后 RAG”的串行模式升级为“图谱事实 + 文档证据”的融合模式。

#### 优化方案

- 识别实体后，查询实体的一跳或两跳图谱邻居
- 同时进行文档向量检索
- 将图谱事实作为高置信结构化上下文
- 将文档 chunk 作为补充解释材料
- 由统一 prompt 生成答案，并明确区分图谱依据和文档依据

#### 适用场景

- 疾病治疗
- 疾病症状
- 药品适应症
- 疾病和药品之间的关系解释
- 病因、预防、并发症综合回答

#### 验收标准

- 答案同时利用图谱事实和文档片段
- 来源区能分别展示图谱来源和文档来源
- 图谱无结果时仍能平滑回退到 RAG

### 5.2 医学安全护栏

#### 目标

降低医疗问答中的误导风险，避免系统给出过度确定的诊断、剂量或治疗承诺。

#### 优化方案

- 高风险意图识别：急症、诊断、处方、剂量、孕妇/儿童用药
- 高风险问题增加安全提示
- 资料不足时明确拒答
- 不输出确定诊断
- 不替代医生建议
- 对急症问题建议及时就医

#### 验收标准

- 用药剂量类问题不会直接给出危险建议
- 急症类问题能给出就医提示
- 无资料问题不会编造答案

### 5.3 性能优化

#### 优化方案

- embedding 批量调用，减少大文档入库耗时
- pgvector 建立合适索引
- 异步任务增加状态：`PROCESSING`、`EMBEDDING`、`INDEXING`、`READY`、`FAILED`
- 模型调用增加超时、重试和错误分类
- 长文档处理增加任务进度

#### 验收标准

- 大文档上传后状态更清晰
- 检索延迟稳定
- 模型接口异常时用户能看到明确错误

### 5.4 前端体验优化

#### 优化方案

- 来源卡片区分图谱来源和文档来源
- 回答过程展示状态，例如：
  - 正在识别实体
  - 正在查询知识图谱
  - 正在检索文档
  - 正在生成回答
- 知识库页面显示处理进度和失败原因
- 历史会话支持搜索
- 高风险医疗回答增加醒目的提示区域

#### 验收标准

- 用户能看懂答案来自哪里
- 上传文档失败时能看到原因
- 流式回答过程更清晰

### 5.5 工程化部署

#### 优化方案

- 增加 Docker Compose：后端、前端、PostgreSQL、pgvector
- 增加 `.env.example`
- 数据库迁移从 `schema.sql always` 迁移到 Flyway 或 Liquibase
- 增加 Actuator 健康检查
- 增加基础 CI：后端 compile、前端 build、测试执行
- 分离开发配置和生产配置

#### 验收标准

- 新环境可以按文档稳定启动
- 数据库结构演进可追踪
- CI 能在提交时发现编译和构建问题

## 6. 推荐实施计划

### 第一阶段：基础安全和评估

目标：先解决影响可信度和后续优化判断的问题。

任务：

1. 向量检索增加用户隔离
2. 向量 metadata 增加 `user_id`
3. 建立 RAG 评估数据结构
4. 增加基础评估命令
5. 增加问答链路调试日志

验收：

- 多用户隔离测试通过
- 至少 20 条评估样例可运行
- 问答日志能显示路由和召回信息

当前已落地的第一批基础项：

- 用户上传文档向量写入 `user_id` metadata
- 在线 RAG 检索按当前登录用户过滤向量
- 文档删除按 `knowledge_id + user_id` 删除向量
- 启动重建向量时保留知识库所属用户
- 问答链路记录路由、实体、意图和 RAG 命中摘要
- 新增 `evaluation/rag_eval_samples.jsonl` 作为基础评估集
- 新增 `RagEvaluationDatasetPrinter` 用于验证评估集格式
- 评估集已扩展到 24 条样例，覆盖 KG、RAG、HYBRID、MEMORY、MISSING、SAFETY
- `SourceItem` 已扩展来源类型、文档标题和 chunkIndex
- 前端来源卡片已支持展示“图谱 / 文档”来源类型和文档片段信息

本地验证命令示例：

```bash
cd backend
mvn -DskipTests compile
mvn exec:java -Dexec.mainClass=com.kgqa.data.RagEvaluationDatasetPrinter
```

注意：项目使用 Java 17+ 语法，运行 Maven 前需要确保 `JAVA_HOME` 指向 JDK 17 或更高版本。

### 第二阶段：RAG 效果提升

目标：提升文档问答质量。

任务：

1. 增加查询改写组件
2. 扩大召回候选并增加重排
3. 优化文档分块
4. 扩展 SourceItem 文档来源字段
5. 前端展示文档标题、分数和片段

验收：

- 评估集 source hit rate 提升
- 多轮追问更稳定
- 来源展示更清晰

### 第三阶段：知识图谱增强

目标：提升结构化事实问答和可解释性。

任务：

1. SPARQL 返回结构化结果
2. 图谱来源结构化
3. 扩展常见模板
4. 增强 SPARQL 校验和错误分类
5. 前端展示图谱实体关系来源

验收：

- 图谱回答能展示实体、关系和值
- 比较、统计、路径类问题具备扩展基础
- KG 失败时可稳定 fallback 到 RAG

### 第四阶段：GraphRAG 和产品化

目标：形成更完整、更有展示价值的医疗问答系统。

任务：

1. 实现图谱邻居检索
2. 融合图谱事实和文档 chunk
3. 增加医学安全护栏
4. 增加 Docker Compose 和环境模板
5. 增加健康检查和 CI

验收：

- GraphRAG 问答能同时显示图谱和文档依据
- 高风险医疗问题有安全处理
- 项目可以更容易部署和演示

## 7. 暂不建议优先做的事项

以下内容不是不能做，但不建议在 P0/P1 阶段优先投入：

- 盲目更换更大的聊天模型
- 直接引入复杂 Agent 工作流
- 大规模重构前端 UI
- 同时接入多个图数据库
- 在没有评估集前反复调 prompt
- 过早做多租户权限体系的复杂化设计

原因是这些改动成本较高，但在当前阶段不一定直接提升系统可靠性和回答质量。

## 8. 决策点

开始实施前，需要确认以下事项：

1. 是否按推荐顺序从 P0 开始？
2. 是否接受旧向量数据需要重建或迁移？
3. 评估集是否先由项目内样例构造，后续再人工补充？
4. 是否优先保证本地演示效果，还是优先向生产部署靠拢？
5. GraphRAG 是否作为后续重点展示能力？

确认后，可以将本计划拆分为详细实施任务，并逐阶段落地。
